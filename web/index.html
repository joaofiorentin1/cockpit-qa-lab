01 · ARCHITECTURE

One simulator, many clients

A single Python process owns the vehicle state. Every screen, the QA runner and the hardware adapters read and change that state through the same HTTP API, so what a test asserts is exactly what the cockpit shows.

CLIENTS
Web cockpitweb/ · HTML, CSS, JS · polls every 450 ms
3D clusterUnity WebGL · polls /api/state
AdaptersSocketCAN bridge · Appium
HTTP / JSON
server.py
Cockpit state machinecockpit.py · gear, speed, door, ignition, connectivity, media · interlocks
QA runnerqa.py · runs scenarios in-process, records expected vs actual
ADB · VHAL
OPTIONAL
Android Automotiveofficial AAOS emulator · screen streamed, speed injected

Python standard library only: no framework, no database. Starting the lab is python3 server.py.

02 · SIGNAL FLOW

From a click to the cluster

  1. Command A button sends POST /api/events with an event, e.g. {"event":"gear_set","value":"R"}.
  2. Interlock check cockpit.py validates it against the safety rules. A refused command answers 400 with the reason and changes nothing.
  3. New state Accepted commands update the state and append an entry to the event log.
  4. Render Every client polls GET /api/state and redraws: the web cockpit, the 3D cluster and the telemetry page.

04 · VALIDATION SCENARIOS

What each scenario proves

VALIDATION TAB

Pick a scenario on the Validation tab and press Run validation. Python drives the cockpit step by step; each step records the expected and the actual state and is marked PASS or FAIL. The JSON report is the evidence.

01

Phone reconnection & media recovery

Play → disconnect the phone → reconnect. Media must resume by itself.

Recovery after a connectivity drop
02

USB connectivity fallback

Connect USB → turn Bluetooth off (projection must stay) → unplug USB (projection drops).

Redundant channels
03

Reverse gear & rear camera

Engage R (camera on) → reverse at 8 km/h → 25 km/h is refused → stop → P (camera off).

Signal + derived function + limit
04

Door / reverse interlock

Open the door → reverse is refused → close the door → reverse is accepted.

Negative test: the system must say no
05

Gear selector interlock

D at 60 km/h → P and R refused → N allowed → slow to 0 → P.

Positive and negative cases
05 · DEFECT & ROOT CAUSE

A failure you can reproduce on demand

  1. Inject On Validation, choose scenario 01 and enable Inject a reproducible defect.
  2. Observe The run ends in Defect detected · 2/3 checks passed: the phone reconnects but media_playing is false where true was expected.
  3. Investigate The Telemetry timeline shows FAULT · playback failed to recover: symptom, evidence and cause in one place.
  4. Reproduce Run it again and it fails the same way. A deterministic failure is what a developer needs to fix it.

08 · DESIGN DECISIONS

Architecture Decision Records

The reasoning behind each choice is recorded as an ADR in docs/adr/:

  • Zero-dependency Python backend
  • Deterministic state machine as single source of truth
  • Safety interlocks as refused commands
  • In-process QA runner with evidence
  • Fault injection as simulator state
  • HTTP polling over WebSockets
  • Real AAOS via ADB as a separate track
  • Hardware adapters as API clients
  • Layered test strategy
  • Honest simulation and brand boundaries
